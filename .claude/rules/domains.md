## 🌐 도메인 마련하기 — 서브도메인 빌려주기 (`/domains`, 2026-10-25)

웹사이트 프로젝트 소유자가 `<이름>.dshs.dev`를 받아 자기 호스트(Vercel·Netlify·GitHub Pages·Render)에 연결한다. 우리는 서버를 빌려주지 않고 Cloudflare에 **CNAME(+필요하면 TXT)만** 만든다. 설계 `docs/superpowers/specs/2026-10-25-subdomain-lending-design.md`, 계획 `docs/superpowers/plans/2026-10-25-subdomain-lending.md`, 시안 B(내 프로젝트 줄마다 "도메인 마련하기" → 그 자리에서 3단계).
- **이름**(2026-10-25 사용자 요청 — "내 집 마련" 느낌): 화면에 보이는 기능 이름·내비 칸·버튼은 **"도메인 마련하기"**(처음엔 "주소 받기"). 안쪽 설명·단계 안내는 쉬운 말 "주소"를 그대로 쓴다. 옛 설계·계획 문서(`docs/superpowers/`)와 migration·`docs/22` 주석에는 옛 이름이 남아 있다(적용된 기록이라 안 고침).
- **사용자 결정**: 등록된 웹사이트 프로젝트에만, 프로젝트당 1개·**계정당 3개**, 신청·연결·반납은 **소유자만**(팀원 불가), 관리자 **강제 회수**, 이름은 자유·선착순, ~~연결돼도 방문 주소는 자동으로 안 바꾸고 제안 띠 + "바꾸기"~~ → **연결하면 방문 주소는 무조건 `<이름>.dshs.dev`**(2026-11-12, 아래 「연결 = 방문 주소 고정」), **비공개 프로젝트도 받을 수 있다**(2026-11-12), 비로그인은 로그인 화면으로, **소유 확인 토큰 필수**(아래), 권한은 "매우 엄격하게".
- **이름 문구·내 도메인 표시**(2026-10-26 사용자 요청): ① `xn--`로 시작하는 이름(한글 등을 바꾼 punycode — 모양 비슷한 글자로 공식 주소를 흉내 낼 수 있어 계속 막음)은 `validateName`이 `reserved`가 아닌 `idn`으로 돌려주고 "한글 같은 영어가 아닌 이름(xn--로 시작)은 아직 쓸 수 없어요…"로 안내한다(예전엔 "사이트에서 쓰려고 남겨 둔 이름"으로 보여 헷갈림). DB 함수는 둘을 구분하지 않으므로 `name_reserved` 문구는 두 경우를 함께 적음. ② 내 웹사이트 프로젝트의 방문 주소가 호스트 기본 주소가 아니라 이미 내 도메인(예: `https://dshs.dev`)이면 `DomainList` 줄에 teal 알약 "내 도메인 사용 중"(`customDomainOf`, `src/lib/domains/hosts.ts`)이 붙는다 — 도메인 마련하기로 받은 주소가 있는 줄·`*.dshs.dev`·localhost·IP·프리셋/`OTHER_DEFAULT_HOST_SUFFIXES`(workers.dev·web.app 등) 호스트 기본 주소는 제외. 모르는 무료 호스트는 내 도메인으로 잘못 표시될 수 있다(목록에 추가). **알약이 붙은 줄은 "도메인 마련하기" 버튼을 숨기고 알약만 둔다**(2026-10-26 사용자 요청 — 이미 도메인을 쓰는데 새 주소를 또 받으라는 건 어색함). 방문 주소가 도메인 마련하기로 받지 않은 `*.dshs.dev`(직접 DNS를 만든 `xn--…dshs.dev` 등)여도 `dshsAddressOf`(`hosts.ts`)가 잡아 같은 알약·버튼 숨김. 받은 주소가 있는 줄은 그대로 "관리".
- **확인 먼저, 연결은 그다음**(2026-10-26 사용자 요청 — 3단계 연결 확인을 안 했는데도 주소가 그냥 열려서 확인 없이 쓰고 있었음): 단계 순서가 **① 이름 → ② 내 사이트에 확인 코드 넣기 → ③ 호스트에 연결하기**. CNAME이 DNS only라 요청이 우리를 안 거쳐서 헤더·경고를 끼울 수 없으므로, **확인 전에는 진짜 연결을 만들지 않는다**. 설계 `docs/superpowers/specs/2026-10-26-domain-verify-first-design.md`, 계획 `docs/superpowers/plans/2026-10-26-domain-verify-first.md`.
  - ① 예약 직후 **자리표시**(`createPlaceholder`, `activate.ts`): proxied AAAA + Bulk Redirect `<이름>.dshs.dev/` → `https://dshs.dev/pending-domain/<이름>`(경로·쿼리 안 붙임, 302). 경고 페이지 `src/app/(nav)/pending-domain/[name]/page.tsx`는 공개·noindex·DB 안 읽음(주인·프로젝트 안 드러냄). 최선 노력 — 못 만들면 주소가 DNS부터 안 풀릴 뿐. id는 `cf_record_ids`에(`subdomain_set_placeholder_records`), 반납·③ 연결 때 같이 지워짐.
  - ② "내 사이트 원래 주소" = **프로젝트 방문 주소로 고정**(2026-11-07 사용자 요청 — 예전엔 미리 채우기만 해서 도메인 화면에서 프로젝트와 다른 사이트를 적어 붙일 수 있었음): 판정 `siteLockOf`(`src/lib/domains/site-lock.ts`, 테스트 있음) — 방문 주소가 `siteAddressFor`로 잡히면 그 주소만(입력칸 읽기 전용 + "다른 사이트에 붙이려면 프로젝트 수정에서 방문 주소를 먼저 바꿔요" 링크), 방문 주소가 없거나 직접 도메인·다른 `*.dshs.dev`면 입력칸 대신 "프로젝트 방문 주소 고치기"(`/projects/<id>/edit`), 방문 주소가 이미 이 주소(`<이름>.dshs.dev` — "바꾸기" 뒤 다시 확인, 대곽나루에서 옮기기)일 때만 예전처럼 직접 적는다. 서버 액션 `setSiteAddress`도 행·프로젝트 url을 읽어 같은 규칙으로 거절(DB 함수는 안 바꿈 — 서비스 키 전용이라 서버 액션이 유일한 입구) → `setSiteAddress` → `subdomain_set_site`(바뀌면 확인 기록 지움) → 토큰을 **원래 주소에서** 확인(`verifySubdomain`이 `site_verified_at` 없으면 원래 주소를 봄, 자동 확인 포함) → `subdomain_verify_site`. 원래 주소 판정 `siteAddressFor`(`hosts.ts`) — 프리셋 9곳 기본 주소만, GitHub/GitLab Pages는 경로 유지, `checkSite`는 기준 URL(경로 포함)을 받는다. "AI에게 보낼 글"은 ②로 옮기고 첫 두 줄을 "내 웹사이트(<원래 주소>)에 … 주소를 붙이려고 해. / 먼저 이 사이트가 내 것이라는 걸 확인하는 코드를 넣고 다시 배포해 줘."로 바꿈(사용자 확인).
  - ③ `connectHost`: `site_verified_at` 없으면 거절, 호스트는 ②의 `site_host`로 고정. 대상이 곧 사이트인 호스트(`targetBoundToSite` — Netlify·Cloudflare Pages·GitHub/GitLab Pages·Render·Workers·Firebase)는 CNAME 값(바로가기는 보낼 곳)이 확인한 사이트 호스트 이름이어야 함(입력칸 읽기 전용). Vercel·Railway는 묶을 수 없어 연결 뒤 실제 주소 확인이 최종 판정(남는 틈). 자리표시를 지운 뒤 CNAME·TXT를 만들고, **바로가기도 여기서 바로 만든다**(옛 "토큰이 처음 확인될 때 켜기" 없어짐). 바로가기 행에 `redirect:` 항목이 없으면 토큰이 보여도 연결됨으로 안 침(`connectionLive`). DB `subdomain_connect`가 `not_verified`·`host_mismatch`·`target_mismatch`로 같은 규칙을 강제하고 `connected_at`을 기록.

  - **흐름**: 대곽나루 포털 서버 카드 "dshs.dev 주소 받기" → `/domains?naru=<서버 id>`(형식 `^[0-9a-f]{8}$`가 아니면 무시, 로그인 화면을 거쳐도 `?naru=` 유지). 웹사이트 프로젝트가 하나도 없으면 목록 위 teal 안내 + "프로젝트 등록하기"(`/projects/new?type=website&next=/domains?naru=<id>`), 있으면 "대곽나루 서버에 붙일 프로젝트를 골라요" 안내 — 줄이 하나뿐이고 주소가 없으면 그 줄이 `initialOpen`, 방문 주소가 없는 줄도 이 흐름에서는 열 수 있다(`DomainList`의 `naruServerId`). 펼친 패널(`DomainSteps`) 맨 위 `ModeCards`에서 "대곽나루"(학교 서버 · 대곽나루에서 빌린 서버) / "다른 호스트"를 고른다 — `?naru=`로 왔으면 대곽나루가 미리 골라져 있고, 확인 코드·호스트 연결을 시작한 주소는 고르지 못한다. 대곽나루를 고르면 ② 확인 코드·③ 호스트 연결 대신 **① 이름(`reserveSubdomain(…, { naru: true })`) → ② `NaruPanel`**(`host-picker.tsx`): `listMyNaruServers()`(running·stopped만, 허브가 이메일로 주인 확인)의 서버 라디오 목록(`?naru=` 서버 미리 선택, 이미 주소가 붙은 서버는 비활성 + 그 주소) → "연결" → `connectNaru`. 서버가 없으면 "대곽나루에서 서버를 먼저 받아요" + `naruLinkFor` 링크(서버 탭 `https://대곽나루.dshs-app.net/dashboard?view=server`). 연결된 뒤에는 "서버 안에서 8080 포트로 서비스를 열어요…" 안내 + 열기 링크 + "다른 서버로 바꾸기", 방문 주소 제안 띠("바꾸기")는 다른 호스트와 같다.
  - **확인 없음**: 확인 코드(`verify_token`) 단계가 없고, 목록의 `useDomainChecks`(자동 확인)·"지금 확인하기"·"N일 뒤 자동 반납"도 대곽나루 행에는 띄우지 않는다(`useDomainChecks`의 pollKey가 대곽나루 행을 자동 확인 대상에서 뺌 — `DomainList`는 옮기는 중의 ② 확인 결과·토스트를 받으려고 대곽나루 행도 훅에 넘긴다). 서버 주인 확인은 허브가 한다. 연결 순서는 허브 묶기(`PUT /devplatform/servers/{id}/domain`) → 옛 레코드 정리 → proxied CNAME(`<터널 id>.cfargotunnel.com`) → DB. 허브가 안 닿으면 DNS를 하나도 만들지 않고 "대곽나루에 닿지 못했어요…".
  - **프로젝트 등록 복귀**: `/projects/new?type=website`면 종류 "웹사이트"가 미리 체크되고, `?next=`가 `/domains`로 시작할 때만(`safeDomainsNext`, `src/lib/domains/next-path.ts` — `//`·스킴·`\`·제어문자 거절, 열린 리다이렉트 방지) 새 등록이 성공한 뒤 권유 창 없이 `next&project=<새 id>`로 간다. 이 흐름에서만 방문 주소를 **비워도 되고**(`urlOptional`, null로 저장) 안내 한 줄이 뜬다. 수정 폼은 그대로 필수.
  - **매일 점검**(`scripts/check-subdomains.mts` → `runNaruSync`): 대곽나루 행은 토큰 확인·끊김·7일 뒤 반납 대상이 아니다(`checkTargets`가 뺌). 대신 허브에 `POST /devplatform/sync`로 (서버 id, 이메일, 이름) 목록을 보내 묶음을 맞추고, 허브가 "없는 서버"(`gone`)라고 한 행만 `naru_server_gone`으로 반납한다. DB 조회가 실패하면 sync 자체를 부르지 않는다(빈 목록이 허브 묶음을 지우면 안 됨), 허브가 안 닿으면(0/5xx) 건너뛰고 반납하지 않는다. 반납(직접·관리자 회수·프로젝트 삭제/비공개·탈퇴)에도 허브 묶음 해제가 최선 노력으로 따라간다.
  - **비밀 2개**: `NARU_HUB_URL`(`https://hub.dshs-app.net`), `NARU_HUB_KEY`(허브 `~/.hub.env`의 `DEVPLATFORM_API_KEY`와 같은 값) — Worker는 `wrangler secret put`, 매일 점검은 저장소 Secrets(`check-subdomains.yml`). 로그에 이메일·키를 찍지 않는다.
  - **가짜 클라이언트**: `getNaruClient()`(`src/lib/domains/naru.ts`)는 production 또는 `NARU_REAL=1`일 때만 진짜 허브를 부르고(env가 없으면 null → "대곽나루 연결이 아직 준비되지 않았어요"), `next dev`에서는 서버 하나(`fa4e0001`, "시험 서버")를 가진 메모리 가짜를 쓴다(`[naru:fake]` 로그) — `DOMAINS_REAL_DNS`와 같은 방식. 개발에서 `/domains?naru=fa4e0001`로 흐름을 볼 수 있다.
  - **다른 호스트로 옮기기**(2026-11-02): 연결된 대곽나루 줄의 관리 패널 "다른 호스트로 옮기기"(`DomainSteps`의 `moveOutId`, 행 id로 기억 — 반납 뒤 새 주소에 남지 않게) → "새 호스트 연결이 끝나야 대곽나루 연결이 풀려요." 안내 + 취소 + 일반 흐름 ②(내 사이트 확인)·③(호스트 연결). 옮기는 동안은 `connected=false`, 대곽나루로 한 "확인"(`site_host='naru'`)은 새 호스트 확인으로 치지 않고, 대곽나루 연결(DNS·허브 묶음)은 그대로다. ③ 연결이 성공하는 순간 `subdomain_connect`가 `naru_server_id`를 비우고, 그 뒤 `connectHost`가 허브 `unbind`를 최선 노력으로 호출한다(`unbindIfMovedFromNaru`, 실패는 로그만 — 이메일 안 찍음; 안 풀리면 매일 sync가 정리). 새로고침하면 옮기는 중 표시는 사라지고 대곽나루 화면으로 돌아간다(DB에 저장된 ② 주소·확인은 남아 다시 누르면 이어진다). 옮기는 중의 ② 확인은 자동 확인(20초 반복) 없이 "지금 확인하기" 버튼으로(배너에 안내 한 줄). `verifySubdomain`의 대곽나루 조기 반환은 `shouldSkipVerify`(=대곽나루이고 `isSiteStep`이 아닐 때, `naru.ts`)로 분리해 테스트한다.
  - **사라진 DNS 다시 만들기**(2026-11-02): 같은 서버 재연결이 중간에 실패하면(옛 레코드만 지워짐) DNS 없는 active 행이 남는다. 매일 점검이 `runNaruSync` 뒤에 `runNaruDnsRepair`를 돌려, 살아 있는 대곽나루 행마다 Cloudflare에 댓글 `dshs-subdomain:<행 id>` 레코드(`listManaged`)가 없으면 proxied CNAME을 `target`으로 다시 만들고 DB 함수 `subdomain_set_naru_records(p_id, p_record_ids)`(host='naru'·live만, service_role 전용, migration `20261102100000_subdomains_naru_records.sql`, 검증 `docs/22-supabase-subdomains-verify.sql`)로 레코드 id를 기록한다. DB 기록이 실패하면 방금 만든 레코드를 지운다. `--dry-run`은 계획만. 로그엔 다시 만든 주소 이름만. 순서는 고아 레코드 정리 **뒤**(실제 상태를 본 뒤 맞춤). 같은 만들기 로직(`restoreNaruDns`)을 `connectHost`도 쓴다 — 대곽나루 주소를 다른 호스트로 옮기다 옛 레코드를 지운 뒤 실패하면 그 자리에서 CNAME을 되살리고 `subdomain_set_naru_records`로 기록한다(최선 노력, 실패하면 매일 점검). **이 migration이 DB에 없으면 점검이 "함수 없음"으로 실패 1건을 낸다** — 배포 순서의 DB 단계에 포함.
  - **고른 연결 방법 새로고침 유지**(2026-11-02): ModeCards에서 "대곽나루"를 고르면 주소가 `?host=naru`(`withHostParam`, `window.history.replaceState` — 서버 왕복 없음)로 바뀌고, 페이지가 `?host=naru`를 읽어 펼친 줄의 모드 초기값으로 쓴다. "다른 호스트"는 `host`를 지운다. `?naru=<id>`가 있으면 기존대로 늘 대곽나루가 미리 골라진다. 로그인 화면을 거쳐도 `host=naru` 유지.
  - **한도 안내**(2026-11-02): `/domains?naru=`에서 살아 있는 주소가 이미 3개면 "프로젝트를 등록해요" 대신 "주소는 한 사람당 3개까지라 더 받을 수 없어요. 안 쓰는 주소를 반납하면 받을 수 있어요."(등록 버튼 없음, `naruGuideKind`). 매일 sync의 "gone이 절반 넘으면 반납 안 함" 비율 분모는 읽은 전체가 아니라 허브에 실제로 보낸 묶음 수.
  - **배포 순서**: 허브 → 포털 → DB(migration) → 개발자 플랫폼. DB에 `naru_server_id` 열이 없는 채로 코드를 올리면 `loadRow`·`connectNaru`·매일 점검이 깨진다.
  - **서울 입구 상태**(2026-11-08, 대곽나루 허브가 학생 주소를 새 Cloudflare 계정 Pages 중계로 자동으로 붙임 — 설계 `server_connection` `docs/superpowers/specs/2026-11-08-student-site-seoul-relay-design.md`): 허브 `GET /devplatform/servers`의 서버별 `edge`(`queued`·`pending`·`seoul`·`spare`·`spare_quota`·null)를 `parseEdge`로 받아 `NaruServer.edge`. 연결된 대곽나루 줄에 `NaruEdgeStatus`(`src/components/domains/naru-edge-status.tsx`)가 상태와 이유(`edgeNotice`, `src/lib/domains/naru-edge.ts` — 사용자 승인 문구, 테스트 있음)를 보이고 준비 중이면 15초마다 다시 읽는다(10분 뒤 멈춤). `NaruPanel` 연결 버튼 위에 `CONNECT_NOTE`(1~2분 끊김 이유). 학생 주소 DNS는 허브가 PATCH로 회색↔주황만 바꾸고 comment는 그대로 — 매일 점검(`runNaruDnsRepair`)은 레코드 존재만 보니 영향 없음. 숨은 원 주소 `naru-sites-origin-server-NN-relay.dshs.dev`(31자+라 학생 이름 규칙 밖, comment `naru-sites-origin`)는 허브 것 — 건드리지 말 것.
