# 관리자 대시보드 `/admin` 설계

> 2026-11-05 사용자와 브레인스토밍. "사용자 결정"은 사용자가 정한 것, "내 판단"은 설계자가 정한 것(사용자 검토 대상).

## 왜 만드나

- 2026-11-04 Jakal Office가 10초 안에 6번 등록됐다(원인은 폼 버그, `adc5a5a`로 고침). 관리자가 하나씩 들어가서 지워야 했고, 누가 일부러 도배하면 막을 방법이 없었다.
- 사용자 결정: **하루 한 번 열어 "무슨 일이 있었나 / 확인할 게 있나"를 알 수 있고, 문제가 생기면 버튼을 최소로 눌러 대응**할 수 있는 화면 하나.
- 사용자 결정: 댓글·글에 **비속어**가 있는지 최신순으로 훑어볼 수 있어야 한다.
- 사용자 결정: 문제 있는 사람은 **기간을 정해 차단**(무제한 포함). 차단되면 **등록만** 못 한다(로그인·열람은 그대로).

## 목표

1. `/admin` 한 페이지에서 오늘 확인할 것 → 사이트 현황 → 최신 글 → 차단 목록 → 주소 관리를 위에서 아래로 본다.
2. 처리할 것이 없으면 맨 위 "확인할 것 없음" 한 줄로 끝난다.
3. 모든 대응(지우기·차단·주소 회수·비공개 전환)은 **그 줄에서 버튼 → 확인 한 번**으로 끝난다. 원래 페이지로 이동할 필요 없음.
4. 차단은 DB에서 막는다 — 화면을 거치지 않는 API 호출도 거절.

## 하지 않는 것

- 사용자 신고 기능(이번엔 자동 골라내기만).
- 관리자 여러 명·역할 구분. 관리자는 지금처럼 `ts250024@ts.hs.kr` 하나(`isDeveloper()` · DB `is_admin()`).
- 글 "숨기기"(테이블마다 숨김 칸 + RLS가 필요). 프로젝트만 기존 `visibility`를 `private`로 바꾸는 것으로 대신한다(내 판단).
- 로그인 차단·계정 삭제.
- Cloudflare 503·GitHub Actions 실패 같은 운영 지표(외부 API 토큰 필요). 나중 과제.
- 그래프·통계 분석. 숫자 몇 개면 충분.

## 피해야 할 것 (기술적으로 돌아가도 실패)

- 관리자가 아닌 사람에게 페이지·데이터가 새는 것. 관리자 아니면 `notFound()`(존재 자체를 숨김, `/domains/admin`과 같음).
- **익명 프로젝트의 작성자가 화면에 드러나는 것.** CLAUDE.md 결정("개발자 계정도 화면에서는 '익명'으로 본다")을 지킨다 — 익명 프로젝트와 그 작성자 표시는 '익명'. 단, "작성자 차단" 버튼은 서버가 `author_id`로 처리하므로 이름을 몰라도 차단할 수 있다(내 판단).
- 지우기를 실수로 누르는 것 — 확인 창 한 번은 있다. 다만 프로젝트 소유자용 "이름 입력 확인"은 관리자에겐 넣지 않는다(버튼 최소화, 내 판단).
- Workers 무료 CPU 10 ms 초과로 503 — 목록은 한 번에 50개 정도로 끊고 "더 보기".

## 화면 구성 (위에서 아래)

공통 톤(PageHero, `bg-white dark:bg-zinc-950`, `max-w-5xl`, 모바일 대응)을 따른다. 섹션 색은 rose 계열 또는 zinc(내 판단 — 설계자가 `SECTION_COLORS`에 `admin` 추가).

### 1. 오늘 확인할 것

자동으로 골라낸 항목. "확인함"을 누르면 사라지고 다시 안 뜬다. 항목마다 이유 한 줄 + 대응 버튼.

| 골라내는 것 | 기준(내 판단, 설계자가 조정 가능) | 버튼 |
|---|---|---|
| 비속어가 걸린 글 | 아래 「비속어 목록」에 걸림 | 지우기 · 작성자 차단 · 확인함 |
| 몰아서 올린 것 | 같은 사람이 10분 안에 같은 종류를 3개 이상(프로젝트·팁·해줘·댓글) | 하나만 남기고 지우기 · 작성자 차단 · 확인함 |
| 가이드 위키 큰 삭제 | 한 번의 수정에서 내용이 절반 이상 줄어듦(`guide_revisions.stats` 활용) | 되돌리기(기존 되돌리기 기능) · 작성자 차단 · 확인함 |
| 문제 있는 주소 | `subdomains.status`가 끊김(`broken`) 상태 | 주소 회수 · 확인함 |
| 차단 기간이 끝남 | 어제~오늘 끝난 차단 | 다시 차단 · 확인함 |

### 2. 사이트 현황

오늘 / 어제 / 최근 7일 숫자. 새 가입, 새 프로젝트, 프로젝트 댓글, 팁, 팁 댓글, 해줘, 위키 수정, 프로젝트 방문(`project_clicks`), 연결된 주소 수, 지금 차단 중인 사람 수. 날짜 경계는 **한국 시간(KST)**.

### 3. 최신 글 (최신순 한 줄)

- 대상: 프로젝트(이름·한 줄 설명·설명 앞부분), `project_comments`, `tips`, `tip_comments`, `ideas`(해줘), `guide_revisions`, 프로필 변경(`users` 닉네임·소개 — 변경 시각 칸이 없으면 가입 순으로만, 설계자 판단). 공지(`announcements`)는 관리자가 쓰므로 뺀다. (정정 2026-11-05: 공지는 로그인한 누구나 쓸 수 있어 차단 가드는 붙였다. 최신 글 목록에는 아직 없음)
- 줄마다: 종류 표시, 쓴 사람(익명 프로젝트는 '익명'), 시각, 내용 앞부분, 비속어는 빨갛게 표시. 버튼: 지우기 · 작성자 차단 · 원래 페이지로.
- 종류 필터 칩(전체/프로젝트/댓글/팁/해줘/위키/프로필), 50개씩 더 보기.
- 비공개 프로젝트도 보인다(관리자는 원래 볼 수 있음).

### 4. 차단 목록

- 지금 차단 중인 사람: 이름, 끝나는 날(또는 "무제한"), 이유, "풀기" 버튼.
- 익명 프로젝트·그 댓글에서 건 차단은 목록에서도 '익명 작성자'로 표시한다(`user_bans.from_anonymous` 같은 표시, 내 판단). "몰아서 올린 것"도 익명 항목은 '익명'으로만 묶어 보여 준다.
- 차단 걸기는 어디서든(오늘 확인할 것·최신 글·이 목록의 "사람 찾기") 같은 작은 창: 기간 선택(1일 / 7일 / 30일 / 무제한 — 사용자 결정: 무제한 포함) + 이유 한 줄(선택) + "차단".

### 5. 주소 관리

지금 `/domains/admin`의 표(`AdminDomainTable`)를 이 섹션으로 옮긴다. `/domains/admin`은 `/admin#domains`로 보낸다.

## 차단 동작

- 사용자 결정: **등록만 막는다.** 로그인·열람·내 글 삭제는 그대로.
- 막는 것: 프로젝트 등록, 프로젝트 댓글, 팁, 팁 댓글, 해줘, 가이드 위키 수정, 주소 받기(`subdomains` 새 행).
- 내 판단: **이미 쓴 글의 수정도 막는다**(차단된 사람이 기존 프로젝트 설명을 욕설로 바꾸는 우회 방지). **프로필 닉네임·소개 변경도 막는다**(같은 우회) — 로그인 때 도는 프로필 upsert(같은 값 다시 쓰기)는 깨지지 않게, 값이 실제로 바뀔 때만 거절. 하트·좋아요·즐겨찾기는 막지 않는다.
- DB: `public.user_bans(user_id, until timestamptz NULL = 무제한, reason, created_at, created_by)` + `public.is_banned(uid)`(SECURITY DEFINER, `search_path=''`, `until IS NULL OR until > now()`). 위 테이블들의 INSERT(그리고 내 판단대로면 UPDATE) RLS 정책·RPC에 `NOT (select public.is_banned((select auth.uid())))`. 서비스 키·SECURITY DEFINER 경로 중 사용자 대신 쓰는 것(RPC로 등록하는 기능이 있다면)도 확인. `user_bans`는 사용자 키로 읽기·쓰기 불가(본인 차단 여부는 `is_banned` RPC로만).
- 화면: 차단된 사람이 등록 폼·댓글 칸을 열면 "○월 ○일까지 글을 쓸 수 없어요"(무제한이면 "관리자가 풀 때까지") 안내, 버튼 잠김. DB 거절 오류도 같은 문구로 바꿔 보여 준다.
- 기록: 차단·풀기·관리자 삭제는 남긴다(`admin_actions` 같은 표 — 누가/언제/무엇을, 설계자 판단). 지운 글 내용은 남기지 않는다.

## 비속어 목록

- `src/lib/admin/profanity.ts`에 한국어 비속어·변형(초성, 사이 공백·특수문자 끼우기, 숫자 치환 일부) 목록과 검사 함수. 테스트 포함.
- 화면에서 표시만 한다(등록을 막지 않음 — 사용자는 "확인"을 원했지 자동 차단을 원하지 않았다).
- 오탐(예: "시발점")은 예외 목록으로.
- 목록 원문이 저장소(PUBLIC)에 올라가는 건 괜찮다(내 판단).

## 데이터 접근

- 페이지는 `force-dynamic`, 서버에서 `getUser()` + `isDeveloper()` 확인 뒤 `createAdminClient()`(서비스 키)로 읽는다. 미들웨어 보호 라우트에 `/admin` 추가.
- 대응 버튼은 서버 액션(`src/lib/admin/actions.ts`, 라우트 그룹 밖) — 액션마다 `getUser()` + `isDeveloper()` 다시 확인 후 서비스 키로 실행. 삭제 시 연결된 것(예: 프로젝트 → 주소 반납·Cloudflare 레코드, Cloudinary 이미지) 처리는 기존 삭제 함수(`deleteProject` 등)의 순서를 재사용.
- "확인함" 기록: `public.admin_dismissals(kind, item_id, dismissed_at)` — 서비스 키 전용(RLS 켜고 정책 없음).
- 헤더 프로필 메뉴에 관리자에게만 "관리자" 링크.

## 개인정보

- 차단 기록(누가·언제까지·이유)은 새로 저장하는 개인정보 처리다. `.claude/rules/privacy.md` 규칙상 처리방침 본문(`src/lib/privacy/policy.ts`)에 적어야 하고, 본문이 바뀌면 **전원 재동의 팝업**이 뜬다. → 아래 사용자 결정대로 하트·댓글 작업과 묶는다.
- 탈퇴(`withdraw_account`) 시: 차단 중이면 탈퇴 후 같은 이메일로 다시 가입해 피하지 못하게, **차단이 끝날 때까지 이메일 해시(SHA-256)와 끝나는 날만** 남기고 나머지(이유·user_id)는 지운다(내 판단, 처리방침에 적음). 가입 때 해시가 걸리면 같은 차단을 다시 건다. `admin_dismissals`·`admin_actions`의 그 사람 행은 user_id를 지운다.
- 사용자 결정(2026-11-05): 처리방침 수정·재동의는 하트·댓글 작업(같은 시기 재동의 예정)과 **한 번에 묶어** 팝업이 한 번만 뜨게 내보낸다.

## 순서

- `project_comments`·`project_hearts`는 운영 DB에 이미 있지만 migration·코드는 하트·댓글 작업(`docs/superpowers/specs/2026-11-04-hearts-comments-design.md`, 다른 세션 진행 중)에 있다. **그 작업이 main에 머지된 뒤** 이 기능의 차단 정책·최신 글을 `project_comments`에 건다(`reviews`에는 걸지 않음, 내 판단).

## 설계자에게 맡기는 것

- 레이아웃 세부, 색, 아이콘, 모바일 배치(넓은 표는 카드형으로).
- 골라내기 기준 숫자(10분/3개, 절반 이상 삭제 등) 조정.
- 쿼리 묶는 방식(RPC 하나로 현황 숫자를 한 번에 등) — CPU·왕복을 줄이는 쪽으로.
- 기존 `/domains/admin` 코드 재사용 범위.

## 문서

- 새 기능 문서 `.claude/rules/admin.md`(`paths:` 포함) + CLAUDE.md 「기능별 문서」 표에 한 줄, 보호 라우트 목록에 `/admin`.
